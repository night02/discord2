# Veylor V0.3.7 — watchdog de inicialização e downloads resilientes

A V0.3.7 sucede a beta V0.3.6, preservada em [GitHub Releases](https://github.com/night02/discord2/releases).
O código novo é desenvolvido em branch separada e não atualiza o Render/PostgreSQL.

## Atualização Windows

1. O cliente abre a release **oficial** `night02/discord2` e confere tag, dois assets esperados, tamanhos e manifesto `SHA256SUMS.txt`. Nenhum token de sessão é enviado.
2. O arquivo é baixado para `*.partial` com limite de tamanho e 30 segundos de tolerância entre chunks. Apenas falhas transitórias (conexão, timeout, HTTP 429/500/502/503/504 e download incompleto) geram até **3 tentativas**. Falhas de checksum ou origem são **terminais**, nunca são tratadas como sucesso.
3. O usuário confirma a instalação. O sidecar verifica SHA-256 novamente, aguarda o processo antigo encerrar e cria backup do diretório anterior.
4. O Inno Setup instala a versão nova; o helper confirma o código de saída, executável e marcador de versão.
5. O helper inicia o aplicativo com um desafio local efêmero. O cliente emite um recibo apenas depois que a primeira tela foi desenhada e a tentativa de restauração da sessão terminou. O helper aguarda até **60 segundos** e observa se o aplicativo fecha. Após receber o recibo, acompanha mais **3 segundos** para detectar falhas imediatas.
6. Se o aplicativo falhar antes do recibo, demorar demais ou sair logo depois, o helper fecha o processo, se necessário, e **restaura o diretório anterior**. Se não conseguir garantir que o novo processo encerrou, preserva o backup sem remover arquivos ainda em uso.
7. Se passar, registra o sucesso e mantém o backup para possível restauração manual. **Não** desfaz mudanças externas de registro do Windows, nem detecta falhas que surjam depois do período inicial de observação.

O helper não confia em certificados fictícios, não desativa SmartScreen e não cria uma identidade Authenticode sem certificado legítimo. A assinatura digital Windows continua opcional para esta beta.

## Logs

Os eventos de atualização são gravados localmente em `%LOCALAPPDATA%\Veylor\Logs\updates.log`, com rotação em 512 KiB (`updates.log.1`). O menu lateral do Windows possui **Logs de atualização** para abrir a pasta.

O logger usa identificadores de eventos, sem incluir senha, sessão, endereços temporários de download ou chaves privadas. Os logs são diagnósticos e não substituem a validação de integridade.

## Validação e limitações

- `flutter analyze` e `flutter test`: testar recibos, processo encerrado, timeout, arquivos inválidos e classificação de erros com retentativa limitada.
- **CI Windows**: gerar instalador e sidecar, instalar, rejeitar SHA incorreto, falhar na checagem de versão, **simular falha de inicialização**, comprovar rollback, instalar atualização válida e desinstalar.
- Android e Linux: builds regressivos, junto de testes de API e saúde do PostgreSQL.
- O teste de recuperação após falha inicial em CI usa injeção de falha **somente com `--no-relaunch`**; o teste completo de abertura gráfica real do usuário deve ser verificado também em um PC Windows.
- A tela de servidores e canais não transforma automaticamente os canais de voz em chamadas: LiveKit permanece uma etapa distinta.
- A versão V0.3.4 mostrada no rodapé das versões anteriores era um **texto fixo**; V0.3.7 consulta a versão instalada.
- Usuários de V0.3.4 precisam instalar manualmente o novo setup, pois essa versão não contém o mecanismo de atualização da V0.3.6. Não presuma que o rótulo antigo indica versão real.
- Publicação beta automática somente após build Windows/Linux/Android e suítes Flutter/API/PostgreSQL passarem no **mesmo commit de main**. Não apagar releases antigas.

Antes de anunciar a nova beta a todos, teste também o instalador no PC real, com caminho de instalação personalizado e proteção do Windows ativada.
