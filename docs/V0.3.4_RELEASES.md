# Veylor V0.3.4 — validação e publicação beta

## Situação

O projeto está no repositório [night02/discord2](https://github.com/night02/discord2). A **visibilidade real deve ser conferida em Settings → General**; o nome e o endereço do repositório não garantem que ele seja público.

A branch de desenvolvimento da V0.3.4 é `feature/veylor-v0.3.4-updates` e segue em PR de rascunho até concluir CI, testar Windows/Android e revisar a distribuição. **Nenhum commit ou workflow atualiza automaticamente o Render.**

## Atualizações do app

- A API `https://veylor-postgres-staging.onrender.com` fornece os metadados `/api/updates/windows` e `/api/updates/android`.
- O aplicativo consulta o feed sem token de sessão, compara o build instalado e só permite páginas `https://github.com/night02/discord2/actions/runs/<n>` ou `.../releases/tag/vX.Y.Z-beta`. Uma release precisa corresponder à versão do feed.
- A instalação é **manual**, nunca baixa ou executa binários silenciosamente.
- Os manifestos do código têm um link de **fallback** para a V0.3.3; **não** anunciar a V0.3.4 até haver uma release real e testada.

## Publicação (ordem segura)

1. Exigir sucesso dos workflows **API tests** (SQLite + PostgreSQL), **Flutter analyze and tests**, **Veylor hosted Postgres health** e **Veylor V0.3.4 preview builds** (Windows + Linux + Android). Todos devem corresponder à revisão testada.
2. Verificar instalação e login em **dois dispositivos reais**. Testar canais, DMs, envio após internet desligada, mensagens duplicadas e sessões após reinício.
3. Integrar as alterações revisadas no branch `main`. O workflow de preview agora também roda em `push` ao `main`, e a verificação da API hospedada também.
4. Aguardar todos os checks do **commit exato do `main`** ficarem verdes. Os builds feitos em PR não substituem os builds de `main`.
5. **Publicação automática beta:** quando o workflow `Veylor preview builds` de um `push` no `main` terminar com sucesso, `Veylor beta Releases` confere os outros workflows do mesmo SHA, verifica o EXE/ZIP/APK/tar.gz e cria automaticamente a prerelease `v0.3.4-beta.<ID do run>` em [GitHub Releases](https://github.com/night02/discord2/releases). Não há sobrescrita de tags, e cada versão aprovada conserva seus instaladores.
6. Verificar os arquivos publicados, SHA256SUMS.txt e o teste de instalação em Windows e Android. Atenção: o APK é debug e o Windows ainda não tem Authenticode. **Não tratar a beta como versão estável.**
7. Se o projeto estiver público, conferir o download numa sessão deslogada.
8. **Somente depois da publicação verificada e de testes de campo:** alterar os manifestos `mobile-release.json` e `windows-release.json` para o número de build instalado e a URL da tag publicada, fazer deploy manual do backend e conferir `/health`, endpoints de atualização, login, canais e DMs. Sem modificar o banco.

**Versões futuras:** o tag beta inclui o número da execução do GitHub, permitindo uma nova publicação em cada alteração de cliente aprovada. O aplicativo ainda precisa receber um build maior e o manifesto da API precisa ser atualizado para anunciar novas versões dentro do app.

## Limitações

- APK debug não tem certificado de assinatura Android permanente; pode exigir reinstalação. A assinatura de release depende de segredos privados do GitHub.
- Instalador Windows não tem certificado Authenticode. Não peça aos usuários para desabilitar proteções.
- O workflow não cria releases automaticamente nem expõe senhas. As GitHub Releases não são garantia de autenticidade criptográfica do editor sem assinatura digital.
- O GitHub Actions pode custar minutos em repositório privado. Evitar builds repetidos e manter releases manuais.
- O PostgreSQL gratuito do Render foi criado com vencimento previsto para **11/11/2026**; migrar/contratar armazenamento duradouro com backup antes de usar em produção real.
