# Veylor V0.3.3 — estabilidade e reconexão

## O que foi implementado

- Cliente Flutter com conexão WebSocket única por sessão (evita múltiplos sockets abertos por chamadas concorrentes).
- `pingInterval` de 20 segundos para detectar conexões mortas e reconexão com intervalos crescentes de 2, 4, 8, 16 e 30 segundos, reiniciados após conectar.
- Restauração de mensagens após reconexão, com busca REST paginada (100 por página) e mesclagem sem duplicatas por ID.
- Polling a cada 30 segundos como fallback para mensagens perdidas quando o WebSocket está indisponível.
- Sessão preservada em armazenamento seguro ao ocorrer falha temporária de rede. Credenciais são descartadas apenas após confirmação de sessão inválida (HTTP 401), e há opção de tentar reconectar.
- Mensagens de canal e DM aceitam um `client_nonce` hexadecimal de 32 caracteres para reaproveitar o mesmo ID em reenvios feitos depois de timeout. O servidor não emite uma segunda notificação para mensagem idêntica repetida e rejeita conteúdo diferente com o mesmo nonce (409).
- Envio conserva o texto digitado até resposta confirmada, sem apagar nova edição feita enquanto o servidor responde.
- Atualizações do Windows e Android consultam exclusivamente a API oficial do Veylor, **sem repassar o token de login**, e abrem somente páginas HTTPS oficiais do repositório GitHub. A instalação continua manual.

## Compatibilidade

`client_nonce` é opcional para clientes antigos. No PostgreSQL, colunas nulas e índices únicos são criados por `ALTER TABLE ... IF NOT EXISTS` e `CREATE INDEX IF NOT EXISTS`, preservando mensagens existentes. SQLite local tem migração não destrutiva equivalente. A nova versão deve ser testada em homologação antes de ser implantada sobre o serviço do Render.

## Testes automáticos

- Flutter: lógica de backoff, merge de páginas, nonce/reenvio, login/widget e validação de URLs.
- SQLite: dois clientes independentes, desligamento simulado do socket de um cliente, 106 mensagens incluindo backlog com paginação, repetição idempotente, DMs e isolamento de terceiros.
- PostgreSQL: verificação de nonce/reenvio para canal e DM, autorização, persistência após reiniciar o processo.
- GitHub Actions: build Windows x64 (instalador e portátil), Linux x64 e APK Android debug. **Não se trata de execução real do aplicativo em dois aparelhos físicos.**

## Teste manual — PC + Android

1. Instale no Windows e no celular a mesma V0.3.3, configurada para `https://veylor-postgres-staging.onrender.com`.
2. Use duas contas de teste distintas. Na conta PC, abra um servidor e gere um convite; entre com a conta do Android.
3. Envie mensagens e DMs nos dois sentidos, verificando nome, ordem e ausência de duplicatas.
4. Desative Wi-Fi/dados do celular por 1 a 3 minutos enquanto o PC envia mensagens; ative a conexão e verifique se todas aparecem sem precisar relogar. Teste também alternar de canal antes da reconexão.
5. Simule um timeout de envio e tente novamente sem mudar o conteúdo: o banco deve conter apenas uma cópia; em caso de falha, o texto não deve desaparecer.
6. Feche e abra o app; confirme que a sessão ainda existe após uma falha temporária, e que sair da conta realmente interrompe a reconexão.
7. No app, toque em Verificar atualização; confirme que abre apenas um link GitHub do projeto e **não baixa/executa** arquivos automaticamente.

## Critérios de publicação

- Todos os testes de API (SQLite e PostgreSQL), Flutter e builds multi-OS devem passar no GitHub.
- Uma falha/cancelamento em qualquer job de build impede o fluxo manual de prerelease.
- Apenas depois de verificar a V0.3.3 em dois dispositivos reais, publicar prerelease e atualizar o manifesto de versões da API no Render.
- Não alterar a base de produção ou migrar contas automaticamente durante esta etapa.
- O PostgreSQL gratuito da homologação expira em **11/11/2026**; antes de usar com usuários reais, migrar para armazenamento persistente com backup e retenção adequados.

## Limites conhecidos

- Os testes automatizados simulam o protocolo de dois clientes, não executam a UI Flutter em um Windows e Android reais.
- Caso o servidor grave uma mensagem mas a conexão caia **antes de retornar confirmação**, a tentativa seguinte com o mesmo `client_nonce` recupera o registro existente. Se o usuário editar o conteúdo para outro texto, o app trata como uma nova mensagem; a mensagem original pode já ter sido entregue.
- Conexões longas offline com mais de 5.000 mensagens demandam ciclos adicionais de polling.
- Não há ainda voz, vídeo, sincronização de presença ou notificações push com o aplicativo fechado.
